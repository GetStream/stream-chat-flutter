## Decisions taken

- **The generated channel and member types map onto today's classes.**
  `lib/src/repository/mapper/channels_mapper.dart` maps `ChannelResponse`, `ChannelConfigWithInfo`,
  `ChannelMemberResponse`, `Command` and `ChatPreferences` onto `ChannelModel`, `ChannelConfig`,
  `Member`, `Command` and `ChatPreferences`, the way `users_mapper.dart` does for `User`.
  [15](15-partial-updates.md) used it first; groups 06, 07 and 14 reuse it. This group adds the
  channel-state, query and update envelopes beside them.
- **Every field `ChannelResponse` and `ChannelMemberResponse` declare is reachable on ours,** as a
  field: [15](15-partial-updates.md) promoted the ones v10 parked in `extraData` and renamed it `custom`.
  Three are left out: the channel's `hide_messages_before`, which the server returns on the
  channel-state entry rather than on the channel, its `mute_expires_at`, since a mute's expiry is
  read from `ChannelMute.expires`, and the member's `role`, which neither the iOS nor the Android
  SDK models. The nested config types drop `ChatPreferences.distinctChannelMessages` and
  `Command`'s `createdAt` / `updatedAt`, which ours do not model.
- **The mapper copies `custom` verbatim** (README rule 9). A mapped channel or member still differs from
  a v1 decode in one way: `truncatedBy`, `createdBy` and each member's user go through
  `users_mapper.dart`, which drops the user fields `User` does not model, for group 09 to settle.
- **The mapper is tested through the client,** by [15](15-partial-updates.md)'s
  `updateChannelPartial` tests and this group's one client test file per method.
- **The v2 routes are the v1 handlers.** `lib/chat/routes.go` mounts every operation of this group in
  the shared `coreRoutes`; none is gated, in beta or deprecated. v1's `GET /channels?payload=` is a
  v1-only wrapper that hands its payload to the same `QueryChannels` handler.
- **Moved off `ChannelApi` and `GeneralApi`:** `queryChannel`, `queryChannels`, `updateChannel`,
  `acceptChannelInvite`, `rejectChannelInvite`, `inviteChannelMembers`, `addMembers`, `removeMembers`,
  `truncateChannel` and `queryMembers`, each a `StreamChatClient` method over `ChannelsRepository`.
  The repository does the routing: `getOrCreateChannel` calls the generated `getOrCreateChannel` when
  given an id and `getOrCreateDistinctChannel` otherwise, and the update, member and invite calls each
  build their own `UpdateChannelRequest`. `sync` stays hand-written and moves with the WebSocket's move to v2.
- **A single-channel query answers `ChannelStateResponse`,** a freezed envelope holding the
  `ChannelState`, from `queryChannel`, `watchChannel` and `Channel.query`, `watch` and `create`; the
  unused v10 class of that name goes. An answer read from the offline storage carries a `'0ms'`
  duration.
- **`queryChannelsOnline` returns a `Result`;** `queryChannels` and `queryChannelsWithResult` stay
  streams and still report a failure as a stream error.
- **The membership calls answer `UpdateChannelResponse`** and keep their v10 names, since they share
  one operation: `AcceptInviteResponse`, `RejectInviteResponse`, `InviteMembersResponse`,
  `AddMembersResponse` and `RemoveMembersResponse` are removed. Its `channel` is nullable and its
  `members` non-nullable, as the spec declares them. Truncating answers `TruncateChannelResponse`.
- **`queryMembers` keeps v10's `QueryMembersResponse`** over the spec's `MembersResponse`, which sits
  beside `QueryChannelsResponse` and the other query envelopes.
- **`PaginationParams` stays on every call,** and each request carries only what the server reads:
  `limit` and `offset` for `queryChannels`; the message cursors for a channel query's messages, and
  `limit` and `offset` for its members and watchers; `limit`, `offset` and the four `created_at`
  cursors for `queryMembers`.
- **The channel data is typed:** `CreateChannelData` (the `Channel` constructor and
  `StreamChatClient.channel` take it as `data`, the channel queries as `channelData`) and
  `UpdateChannelData` (`updateChannel`, `Channel.update`) replace the untyped map, named per operation so
  a create-only field never has to sit unused on the update type; `ChannelMemberData` replaces member
  ids in the members, invites, `addMembers` and `inviteMembers`. They hold `members`, `invites`, `team`,
  `frozen`, `disabled` and `custom`. `filter_tags` is left out as not meant for integrators, and
  `config_overrides` and the auto-translation settings because a client cannot set them (401/403 live).
- **`ChannelState.merge`** folds a newer state in, keeping the fields it leaves out, for
  `ChannelClientState.updateChannelState`; the one-off merges elsewhere stay explicit.
- **`ChannelState`, `ChannelModel`, `Member`, `ChannelConfig` and `PredefinedFilter` become plain
  freezed models,** with freezed's `copyWith`: each call site that relied on `null` keeping a value
  merges explicitly. `ChannelModel` and `Member` keep a v1 decoder for the WebSocket, keyed by the
  fields the spec's `ChannelResponse` and `ChannelMemberResponse` declare, so a declared field the
  model leaves out never lands in `custom` on either path. `ChannelConfig` gets the storage codec
  (rule 8).
- **Left out:** `hide_messages_before`, on the channel-state entry and on the channel; the member's
  `role`, which v10 never read either (`Member.copyWith(role:)` goes); a channel state's `threads`.
  `name` and `image` stay in `custom`.
- **`ChannelConfig` keeps its v10 fields.** The ones only `ChannelConfigWithInfo` carries
  (`allowedFlagReasons`, `automodBehavior`, `automodThresholds`, `blocklist`, `blocklistBehavior`,
  `blocklists`, `countMessages`, `customEvents`, `grants`, `name`, `partitionSize`, `partitionTtl`,
  `quotes`, `reminders`) stay out, as on v1; exposing them later is additive. The mapper's TODO stays.
- **`stopWatching` stays hand-written for now:** the generated `stopWatchingChannel` sends no body
  where the endpoint requires one. Fixing the generator or keeping the method hand-written is decided
  separately; when it moves, it takes the spec's name, `stopWatchingChannel`.

## Risks

- When `sync` moves, check a real response decodes: its `events` are the generated `WSEvent` union, which needed a generator patch to decode.
- `sync` lives in `general_api.dart`, not `channel_api.dart`.
- **A member request's `custom` is stored as an entry named `custom`.** The generated `ChannelMemberRequest` always sends `custom`, and the server keeps it as one custom key rather than as the member's custom data, so every member v11 adds reads back with `custom: {'custom': null}` (or its entries nested under it). Accepted and documented in the migration guide; the fix is the server reading it as the custom data, or the generator omitting nulls.
- `queryChannels` drives the channel list controllers and the offline cache; a shape change here is felt everywhere.
- **A zero timestamp decodes differently on v2.** v1 sends Go's zero time as `0001-01-01T00:00:00Z`; v2 encodes timestamps as epoch nanoseconds and sends `0`, which decodes as 1970-01-01. A truncated channel shows it: its `last_message_at` is zero time, so the same channel answers year 1 from a v1 query or WebSocket event and 1970 from `/api/v2/chat/channels`. Nothing in the SDK behaves differently today, since both precede `createdAt` (`lastUpdatedAt` falls back to it, and the read fallback and the `max` against new messages agree), but the two sources disagree on the value. `channels_mapper.dart` reads v2's zero `last_message_at` as `null`; the v1 WebSocket decode still answers year 1 until it moves to v2.
- [08](08-moderation-and-blocklists.md)'s `muteChannel` drops `channelMute`, `channelMutes` and `ownUser` because the generated `ChannelMute` carries a `ChannelResponse?` and a `UserResponse?` where ours needs a non-nullable `ChannelModel` and `User`. `channels_mapper.dart` covers the channel side now; it needs 09 as well. Decide the null case there too — ours are non-nullable, the generated ones are not, the same question [14](14-banned-users.md) records for `BanResponse.user`.
